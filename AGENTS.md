# Working Rules for Liquid

These rules apply to both humans and AI agents working in this repository.

Liquid is a bookkeeping and invoicing system for Swedish companies. It is not a standalone server: it is an app (app id `liquid`) in [Swecial Server](https://github.com/Swecial/swecial-server), like Big Ring and Digolux, but web only (no Unity client). Everything in `server/` is the app's cloud code and web pages.

## Project Communication

- **English Only:** All official project communication must be in English: commit messages, branch names, pull requests, code comments, issue descriptions and documentation. Chat conversations between AI agents and developers may be in other languages.
- **Exception:** text shown to users in the web pages (labels, messages, `LiquidException` messages) is Swedish, since the product is for Swedish companies.

## Agent Instructions Structure

- **`AGENTS.md`** is the single source of truth for all rules, conventions, and workflows.
- **`CLAUDE.md`** points to `@AGENTS.md` for Claude agents.
- **`GEMINI.md`** is a symbolic link pointing directly to `AGENTS.md` for Gemini agents.
- **Important:** Always and only edit `AGENTS.md` if you want to update the rules. Never delete or overwrite the symbolic links manually.

## Branches and Workflow

- One developer: no pull requests. Commit straight to `develop` (the default branch) and push.
- `master` is what runs in production. Release by fast-forwarding `master` to `develop` and deploying (see Deploy).
- Keep commits small and self-explanatory, and verify on a local server before pushing (below). Never force-push.

## Environments

- **Testing:** an agent tests on its own Swecial Server instance (a git worktree of swecial-server with its own data and port), never on the developer's local server or its data.
- **Dev:** the local Swecial Server in `../../swecial/swecial-server` (`~/dev/swecial/swecial-server`). Link this repo once with `./link-app.sh liquid ~/dev/cmbellman/liquid` (it symlinks `server/` to `SwecialServer/apps/liquid/code`), then start it with `./start-server.sh`. The site is at `http://localhost/liquid/`. Local data is plain JSON under `swecial-server/SwecialServer/apps/liquid/classes/`; user accounts are in `SwecialServer/data/users/`.
- **Prod:** the same server as the games: `https://m.swecial.se/liquid/` (HTTPS with Let's Encrypt; `deepthought.swecial.se` answers on plain HTTP only, so use m.swecial.se).
- The file watcher doesn't follow symlinks: **restart the local server after changing a `.cs` file**. `.html` and `.css` changes show on reload. Compile errors only appear in the server console (`compiling liquid` … `CSxxxx`); the old code keeps running when compiling fails.

## Deploy

- Production deploys run from the swecial-server repository: the GitHub Action **CD (Deploy Liquid Cloud Code)** (`deploy-liquid.yml`, input `branch`, default `master`), or `deploy-liquid.ps1` on the server. It pulls this repo into `D:\swecial\liquid` and mirrors `server/` into `D:\data\swecialserver\apps\liquid\code`; the server recompiles by itself, no restart.
- `gh workflow run deploy-liquid.yml -R Swecial/swecial-server -f branch=master`

## Code Layout

- `server/Cloud.cs` – the app's `Cloud` hooks. There is no SDK client, so `beforeSave` turns any SDK save into a harmless object.
- `server/Liquid/` – domain logic, `namespace com.swecial.code`:
  - `Db` data access, `Money`/`Dates`, `Bas` chart of accounts, `Ledger` vouchers, `Reports`, `Statements` (income statement and balance sheet), `Companies`.
  - `Invoicing` customer invoices, `Expenses` + `Categories` everyday purchases with receipts, `BankEvents` other money in and out of the company account, `Securities` the company's funds, `Closing` the year-end closing.
- `server/www/` – pages, `namespace com.swecial.web`: **markup lives in the templates, never in C#.**
  - `x.html` starts with `<% class=WebX %>`, includes `partials/top.part` (head, sidebar, error and message) and `partials/bottom.part`, and holds the page's markup. Shared pieces are partials (`.part`, never served): `dropzone.part`, `expense-form.part`, `invoice-totals.part`.
  - `WebX : LiquidPage` only sets values: `set`/`val` (val HTML-encodes), `rows(key, …)` of `row(…)` objects for `<swe:iterator source="key">` (plus the flag `keyAny`), bools for `<swe:condition>`, `options(…)` for selects. Template syntax is in swecial-server's AGENTS.md ("Templates").
  - Generated graphics stay in C#: the chart and gauges (`FlowChart`) and icons (`Icons`).
- `server/themes/<id>.json` – the themes (see Themes).

## Conventions and Rules

- **Server naming:** class names are snake_case (`voucher`, `customer`), field names camelCase. Fields starting with `_` belong to the server.
- **Company scope:** every class except `membership` has `companyId`. Pages read objects with `Db.getOwned(class, id, companyId)` / `Db.forCompany(...)`, never `Db.get` with an id from the request.
- **Money** is whole öre in a `long` (`Money.parse`/`Money.format`), never `double`. Dates are `"yyyy-MM-dd"` strings, which compare as text.
- **Themes:** every user picks a theme (Inställningar → Utseende; stored on the user as `liquidTheme`). A theme is data: `server/themes/<id>.json` (name, description, `language` sv/en, `extends`, `gauge` beer/tank, `brand`, `clock`, `fonts`, `icons` per place, and **all UI texts by key**) plus `server/www/theme-<id>.css` (tokens and typography, scoped to `body.theme-<id>`). Texts missing in a theme come from the theme it extends, then from `boring`, so a new theme can override only what it wants. In templates a text is `<%t.bar.tab.title%>`; in C# `T("key", args…)` (encoded, `{0}` placeholders), `Tr` (plain) and `Tn` (`.one`/`.many`). A key can't be both a text and a group: use `x.label` for the text. Errors from the books are `LiquidException(swedish, english)`; the theme's `language` picks one. The printable invoice is always Swedish and neutral (a document for the customer). Adding a theme: copy a JSON file, change what you want, add its CSS file; it shows up under Utseende by itself.
- **Names and look:** Boring is the default theme (Swedish, clean and modern SaaS look for everyday business owners: Översikt, Kassaflöde, Likviditetsreserv, Obetalda kundfakturor, Kvitton, Företagskonto, Värdepapper, Kunder, Årsbokslut; neutral dark slate, Inter, tank gauge). The app also offers themed experiences: Puben is a classic pub theme (Swedish, dark wood/brass/amber, Baren, Kranen, animated beer glass, Notan, Pantpåsen, Kassan, Källaren, Stamgästerna, Stängningsdags); Nostromo is a green phosphor ship terminal in corporate English (tank gauge, clock, crate and console icons); Skynet is a crimson-orange autonomous AI terminal in tactical English (tank gauge, clock, reticle, crosshair and shredder icons). Puben's tokens remain the defaults at the top of `style.css`. Charts and icons are inline SVG made on the server (`FlowChart`, `Icons`); the printable invoice stays light.
- **Users aren't bookkeepers:** the everyday pages (invoices, expenses, bank) never ask for accounts, debit or credit. The user picks what something is (an expense `Category`, a `BankEventKind`) and Liquid books it. Accounts and vouchers live under "Avancerat". Keep new features that way.
- **Settings** (Inställningar, `company.html`, `Settings`), stored on the company: invoice numbering (`serial` 1, 2, 3 … with a settable next number, or `date` = invoice date + two-digit serial for the day, `2026102101`), accounting method per fiscal year (`methodsJson`, `cash` default, or `accrual`; a year without a choice has the latest earlier year's, `Settings.accountingMethod(company, year)`) and VAT period (`year` default, `quarter`, `month`; the VAT report defaults to the current one). Serial numbers stay below 1 000 000 000 so they never collide with date numbers, and a new next number must be above every serial already used.
- **Accounting method:** with the cash method (kontantmetoden) a sent invoice gets its number and is booked when paid (1930 D / 300x K / 26x1 K). With the accrual method (faktureringsmetoden) it is booked when sent (1510 D / 300x K / 26x1 K, series F) and the payment clears the receivable (1930 D / 1510 K). Each invoice remembers how it was booked (`voucherId` set when booked at sending), so switching method never books an invoice twice. Expenses are always booked on the day they were paid. With the cash method, unpaid invoices at year end belong to that year: the closing books them as receivables (1510 D / 300x K / 26x1 K) and sets `closingVoucherId`. An invoice paid in a later year than its invoice date that no closing booked gets that receivable when it is paid, dated the year's last day (`closingByPayment`), and the payment clears it (1930 D / 1510 K). Only when the books have no income in the invoice's year (that year was kept elsewhere, invoices booked when paid) may the user tick "take up as income when paid" (`incomeWhenPaid`, `Invoicing.mayTakeUpWhenPaid`), which books the sale on the payment. A registered payment can be undone (`Invoicing.unmarkPaid`), which reverses its voucher and a receivable booked with it.
- **Invoice numbers** are given when the invoice is sent (`Invoicing.nextNumber`): counter `invoice` for serial numbers, `invoice-<yyyyMMdd>` for date numbers.
- **Voucher series:** A manual, F invoices booked when sent (accrual method) or unpaid at year end, I invoice payments, U expenses, B bank events, V funds and securities, S the year-end closing.
- **Source objects own their vouchers:** an expense or bank event that changes or is removed reverses its voucher (dated like the original) and books a new one (`Ledger.reverse(..., fromSource: true)`); its voucher can't be reversed from the voucher page. An edit that changes nothing booked (only the note or receipt) keeps the voucher.
- **Purchases from abroad** (`expense.foreign`, `Expenses`): `eu` services from the EU (box 21), `noneu` services from outside the EU (22), `eugoods` goods from the EU (20): reverse charge, cost D total, 1930 K total, plus 2645 D / 2614, 2624 or 2634 K by rate (boxes 30–32, 48). `import` goods from outside the EU: the same on the customs value (`importBase`, box 50) with 2615/2625/2635 (60–62); customs duty is its own expense. `abroad`: foreign VAT on the receipt, or used abroad: no Swedish VAT, the whole amount is cost. Categories marked `consumedAbroad` (travel, hotel, representation) are always `abroad` when bought abroad (hotels then on 5832), never reverse charge.
- **Sales abroad** (`Invoicing.vatTreatment`, from the customer's `region` and VAT number, fixed on the invoice when sent with `supplyType` goods/services and `customerVatNumber`): an EU business with a VAT number gets no VAT (reverse charge, 3108 goods / 3308 services, boxes 35/39, the EU sales list `Invoicing.euSalesList`, reports `?report=eu`), a customer outside the EU gets no VAT (export, 3105/3305, boxes 36/40); the printable invoice states why. EU consumers pay Swedish VAT. These boxes come from the invoices by invoice date, since the cash method doesn't apply to them.
- **Rules and figures** (`Rules`, page `rules.html` under Avancerat): every figure from laws and Skatteverket that can change (food VAT, the representation base and schablon, prisbasbelopp, the limits for the cash method and VAT periods) lives in `Rules.All` with values by date, a source and `checkedUntil`. Code reads `Rules.value(key, date)`, page scripts get the same table (`Rules.json`), texts take the figures as `{0}`. Never hard-code such a figure elsewhere. Baren's to-do list asks for a check when today's value of a rule isn't checked (`Rules.notChecked`): update the table at least once a year (next year's values, or a later `checkedUntil`). Add new rules (3:12, employer contributions) when payroll is built.
- **Representation** (category `representation`, account 6072, `Representation`): the cost is never deductible; VAT is deducted on at most 300 kr excl. VAT per person (full VAT below that, above it the food rate on 300 kr per person, or Skatteverket's schablon with alcohol; the figures are in `Rules`). The expense keeps the receipt's VAT (`receiptVat`), books only the deductible part on 2641, and requires the documentation: internal/external, number of participants, attendees (name and role) and purpose (also in the voucher text). The receipt reader suggests `aiAlcohol`. Representation abroad is allowed: no reverse charge and no VAT, the whole amount on 6072, and it stays out of VAT return boxes 21/22.
- **Pantpåsen:** a receipt in the bag is an expense with status `inbox` (nothing booked). Sorting it on the expense page books it (status `booked`) and moves on to the next one. Lists and sums of expenses only count `booked` ones (`Expenses.list`); the bag is `Expenses.inbox`. Several files come in one upload (`req.body.fileList`).
- **Receipt reader (AI)** (`ReceiptReader`): a receipt put in Pantpåsen is read in the background by Gemini: with the server's `geminiApiKey` through the Gemini REST API (production; works under any service account), otherwise through the Antigravity CLI (`agy -p … --sandbox --output-format json --json-schema …`, in an empty temp folder with only the receipt; for local development, since agy's sign-in belongs to one OS account). At most two at a time. A failure is classified (`ReceiptReader.Problem`) and kept on the company (`readerProblem*`) until a reading succeeds; Baren and Pantpåsen show it. The answer is checked field by field and stored as a suggestion on the expense (`aiStatus` reading/done/failed, `aiSupplier`, `aiDate`, `aiTotal`, `aiVat`, `aiVatRate`, `aiCategory`, `aiForeign`, `aiCurrency`), which fills in the sorting form. **Nothing is booked from AI output**: the user checks and books. Text on a receipt is data, never instructions (said in the prompt; the schema and the checks enforce it). Amounts in other currencies than SEK are left for the user. The reader is off unless the app's `settings.json` on the server has `receiptReaderCommand` (see README).
- **Own invoices in Pantpåsen:** the receipt reader is told which company it reads for and marks an invoice that company issued (`aiKind=sales`, details in `aiSaleJson`), so it's never booked as a purchase. `Invoicing.draftFromDocument` turns it into a draft (customer found by organisation number or name, or created; rows, dates, references; the original as `documentFileId`, served by `receipt.html?invoice=`), and `Invoicing.registerIssued` registers it with the document's own number: it must be new for the company, and Liquid's series move past it (`reserveNumber`). It's then booked like any sent invoice for the company's method. The sorting page also offers this by hand, and "Läs kvittot igen" re-runs the reader.
- **Funds** (Källaren, `securities.html`, `Securities`): an event (`security_event`) is a purchase (1350 D / 1930 K), a sale (1930 D / 1350 K cost / 8220 gain or loss) or a switch from one fund to another, which is a sale: the gain or loss is booked on the day of the switch (1350 D value / 1350 K cost / 8220), and the new fund's cost is the value sold. The cost of sold units is the holding's average cost (genomsnittsmetoden); selling all units takes all of it. Holdings (units in millionths, cost, the price at the latest event) are worked out by replaying the events, so events are registered in date order and only the latest can be removed (it reverses its voucher). `owned` registers a holding from before Liquid without booking anything. Liquid doesn't know market prices. Funds held on 1 January give a standard income for tax (schablonintäkt, `Rules.FundStandardIncome`, 0,4 % stored as permille, INK2S 4.6 b): the user enters their market value on 1 January per year (`fundValuesJson` on the company), Källaren shows the income and Baren asks for this year's value until it's there. Nothing is booked.
- **Income statement and balance sheet** (`Statements`, Rapporter): the K2 layout (ÅRL bilaga 2, by nature of expense, and bilaga 3) from BAS account ranges, with the same period or day a year earlier. Accounts 8990–8999 (the closing's transfer of the result) are left out of the income statement. The balance sheet's free equity is worked out, not read from 2099: the year's result is the income statement for the calendar year up to the date, everything else on 2000–2079 and 2090–2099 plus earlier results not yet moved by a closing is the retained result, so it always balances before and after a closing. The closing should use `Statements.incomeStatement` for the year's result.
- **Year-end closing** (Stängningsdags, `closing.html`, `Closing`, one `closing` object per company and year): steps that each book what is left of them, read from the books, dated 31 December in series S (sourceType `closing`, not reversible by hand), so a step can be booked again when something earlier changes: unpaid invoices as receivables (cash method, `Invoicing.bookAtYearEnd`), VAT accounts 2610–2649 to 2650, what Skatteverket took from the tax account (preliminary tax 2518, VAT 2650, entered by the user), tax allocation reserves (reserves six years old reversed to 8819, a new one on 8811 / 2110 + (year − 2010) up to `Rules.TaxAllocationShare` of the surplus), income tax (8910 / 2512) and the result (8999 / 2099). Steps book only after the year has ended; before that the page is a preview of the tax. The tax (`Closing.tax`, like INK2S) is the result before tax plus non-deductible costs (`Closing.NonDeductible`) minus tax-free income, plus the standard incomes on reserves (statslåneränta, at least the floor, `Rules`) and on funds, plus the uplift on reversed reserves from before 2021, with a net loss on funds (8220) added back and saved for later gains, minus the deficit from the year before; the surplus is rounded down to whole hundreds of kronor and taxed at `Rules.CorporateTax`. Locking (with the bank balance confirmed) stores the deficit and saved fund losses for the next year (or they are entered on the next closing when the year before wasn't closed in Liquid); no voucher dated in a locked year can be booked (`Closing.requireOpen` in `Ledger.validate`). A year can be reopened (a later locked year first). Not handled yet: depreciation of equipment, group contributions, dividends received, setting off 2518 against 2512 after the assessment, the dividend decision.
- **Kranen and Glaset** (`Flow`) read the bank account's vouchers (1930) and leave reversal pairs out. Glaset's pace leaves money moved to and from funds (series V) out: it isn't spent. The forecast is the unpaid invoices by due date; Glaset is the balance divided by the average money out per month over the last three months.
- **Receipts** are `_file` objects with `companyId`, served only by `receipt.html` to the company's users (links carry `&v=<file id>` so a replaced receipt isn't cached). Uploads use `req.body.files`, which needs swecial-server with multipart support (Swecial/swecial-server PR "Parse multipart/form-data POST bodies"): deploy that before a Liquid version that has it.
- **Bookkeeping rules:** a voucher must balance and use accounts in the chart (`Ledger.validate`). In ordinary operation, a booked voucher is never changed or deleted; mistakes are corrected with a reversing voucher (`Ledger.reverse`), as required by the Swedish Bookkeeping Act (Bokföringslagen). Only invoice drafts can be edited or deleted. Vouchers booked from an invoice can't be reversed by hand.
- **Admin voucher override (test data only):** for cleaning up test transactions prior to going live, admin users (`account.isAdmin`) have an admin action on the voucher page (`voucher.html`, `Ledger.deleteAndRenumber`) to permanently delete a voucher (and optionally its linked reversal pair) and renumber the series sequentially from 1 (updating sequence counters and references). Admins can also renumber all series from `vouchers.html` (`Ledger.renumberAllSeries`). This must never be used on live accounting records.
- **No transactions:** the server has none. Anything that numbers or books takes `Db.Sync` and writes with `Db.commit` (save + saveNow). Keep a business event in one object (rows are embedded as JSON in `rowsJson`) so it is written as a whole. Validate before taking a number, so numbers stay gap-free.
- **HTML escaping:** template values are inserted raw. User text goes through `val()`/`h()` (and `u()` inside URLs); theme texts are encoded already. Never put `<%` in a value.
- **Errors:** throw `LiquidException(swedish, english)` for user mistakes; `LiquidPage` shows it and calls `renderAfterError()`, which sets the page's values again so the form keeps what was typed. After a successful POST, redirect (with `?ok=<key>` for the message) so a reload doesn't post again.
- **Server limits to keep in mind:** only `.html`, `.css`, `.json` and `.ico` are served (put JavaScript inline), POST bodies are urlencoded or multipart (`enctype='multipart/form-data'` for uploads), there is no PDF library (invoices print from the browser), and the cloud code compiler only references what the server references (e.g. not `System.Net.Mail`).

## Known Gaps

- The SDK `list` command has no access control in Swecial Server, so a client with the app's key could read Liquid data. Liquid has no SDK client and its key must never be shipped. A server-side "web only" switch for an app is the proper fix.
- One company per user, the fiscal year is the calendar year, no credit notes, partial payments, SIE export yet.
- Next steps: the annual report (K2) and INK2 figures, SIE export.
